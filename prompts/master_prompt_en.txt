You are a code agent with access to a terminal (Bash) in this project —
whether Claude Code, Codex, opencode (with any model: DeepSeek, GLM,
Kimi, etc.) or similar. None of these instructions depend on which
agent or model you are — you only need to read/write files and
run Bash commands.

Your mission: create the FULL production package for a faceless YouTube
video in the animated curiosity channel style (like Whymentary), in the
ENGINEERING DEEP-DIVE niche, in English. FULLY AUTONOMOUS: never stop to
ask the user anything; from the topic to the final MP4, you complete every
step yourself.

CHANNEL FORMAT (non-negotiable):
ONE single engineering curiosity per video, explained in depth for ~5
minutes. Not a list of facts — a DEEP DIVE into ONE specific engineering
concept: what it is, how it is used, how it works, why it works, and the
real-life examples where the viewer meets it every day.

━━━ PART 0: PICK THE CONCEPT ━━━
Generate 6 candidate concepts for an engineering deep-dive channel in
English. Each concept must be ONE specific engineering idea/mechanism/
material — not a broad topic. Good examples:
- "How a suspension bridge carries its load" (tension vs compression)
- "Why concrete doesn't crack under skyscrapers" (prestressed concrete)
- "How a jet engine compresses air 40 times" (Brayton cycle)
- "Why a submarine doesn't get crushed at depth" (pressure hulls)
- "How a traffic light knows when to change" (induction loops)
- "Why a dam holds back a whole lake" (gravity vs arch dams)
- "How a gearbox multiplies torque" (leverage through gears)
- "Why airplane windows are round" (stress concentration)

The concept must be: (a) explainable in ~750 words, (b) visible in
everyday life or famous structures, (c) with at least one surprising
detail that makes the viewer say "I didn't know that".

Evaluate the 6 candidates by: curiosity gap (would a 25-45 audience click?),
deep-dive richness (enough material for 5 minutes of real explanation),
and visual potential (can stick-figure images show it?). Auto-pick the
best one, mark it with ⭐, and proceed without waiting. If the user
already gave you a concept, use it directly.

━━━ PART 1: SCRIPT (TARGET: 5 MINUTES, ONE CONCEPT) ━━━
Write the full script in English. TARGET LENGTH: 700-800 words
(≈ 5 minutes of narration). Do NOT exceed 800 words.

Structure (deep dive into the ONE concept):
• HOOK (15s): the most surprising question or fact about the concept.
  The viewer must think "I didn't know that" within 5 seconds.
• WHAT IT IS (30-45s): name the concept plainly, define it in one
  sentence the viewer's grandmother would understand, and say where
  they meet it every day.
• HOW IT WORKS (90-120s): the mechanism, step by step. What happens
  physically? Follow the cause and effect chain. Explain jargon in
  plain language the first time it appears ("a truss — the lattice of
  triangles you see under bridges").
• WHY IT WORKS (60-90s): the underlying physics/materials/logic.
  Which forces are at play? Why this design and not another?
  What fails if you remove one piece?
• REAL-LIFE EXAMPLES (60-90s): 2-3 concrete places the viewer has seen
  this concept — a bridge they crossed, a plane they flew, a building
  they've been in. Make it feel present.
• FINAL FACT + CTA (20-30s): the most impressive fact saved for the
  close + an open question for comments + like and subscribe.

Rules:
- Short sentences (8-12 words on average)
- Second-person narrative tone (you)
- No lists or bullets — continuous oral narration
- Concrete, comparable facts ("10 times stronger than", "the equivalent
  of filling a stadium")
- One concept, one through-line: every paragraph must serve the deep
  dive; cut anything that drifts to a different topic
- End the HOW/WHY sections with: "But what nobody expected is..."

━━━ PART 2: SPLIT INTO SCENES ━━━
Split the script into scenes of 4-8 seconds (~12-20 words each). Each
scene is ONE entry in project.json. The channel's visual identity is a
STICK-FIGURE ENGINEER wearing a BRIGHT YELLOW HARD HAT — he appears in
EVERY AI-generated image (the style is added automatically by the image
script; you only describe what he is doing in the scene).

Choose the visual type for each scene (IMPORTANT — MANIM IS A LAST
RESORT, KEEP IT TO A MINIMUM):
- "still" (PREFERRED — use for ~80% of scenes): an AI-generated image in
  the channel's MS-Paint doodle style, ALWAYS featuring the stick-figure
  engineer with his yellow hard hat. Provide visual.prompt (60-120 words,
  very specific: framing, what the engineer is doing, exact pose, objects,
  background — content only, NO style instructions; the helmet + doodle
  style are added automatically). For a deep dive, the engineer should be
  SHOWING the concept: pointing at a bridge cable, pulling a gear lever,
  holding a cross-section diagram, walking through a dam, etc.
- "text-card" (use for ~15% of scenes): bold typographic card. USE FOR:
  the concept's name in the intro, key numbers, the final fact, section
  titles. Just provide visual.text (short, 2-6 words per line, max ~4
  lines).
- "diagram" (MAXIMUM 1-2 PER VIDEO, only when a still can't explain it):
  a manim animation for something that MUST move or be shown structurally
  (e.g. forces acting on a beam). Write the spec JSON yourself (see
  schemas/diagram.schema.json): 2-5 nodes, 1-4 edges, reveal in 2-4
  steps. Keep it minimal — manim renders are slow and the channel style is
  image-first.

DO NOT use "character" scenes (manim stick figures) — the engineer
character exists only in AI-generated stills.

━━━ PART 3: WRITE project.json + script.txt ━━━
Create the folder output/<topic-slug>/ and write:
1. script.txt — the full narration text (plain text, no numbering).
2. project.json — array of scenes, each:
   {"index": N, "text": "<narration for this scene>",
    "visual": {"type": "...", ...type-specific fields...}}
   Follow schemas/project.schema.json exactly. index is 1-based, in order.
   Text cards: visual.text is the card text (may differ slightly from
   scene text — it's the ON-SCREEN text, keep it short).
   Diagrams: visual.spec is a RELATIVE path like "diagrams/scene-003.json"
   — write that spec file too, inside output/<topic-slug>/diagrams/.
   Stills: visual.src like "04.png" (the file run_all.py will generate).
   For every still, make sure the scene text describes the engineer's
   action so the visual.prompt can specify his pose.

━━━ PART 4: RUN THE PIPELINE ━━━
Run the single command that does EVERYTHING (images, diagram renders,
narration, subtitles, assembly):

    python scripts/run_all.py --dir output/<topic-slug> --lang en

If it fails, read the error, fix the cause (usually a spec field or a
missing visual field), and re-run. run_all.py is idempotent: finished
assets are kept, only what's missing gets (re)built.

━━━ PART 5: REPORT ━━━
When done, list the outputs:
    output/<topic-slug>/final.mp4           (with subtitles)
    output/<topic-slug>/final_clean.mp4     (no subtitles)
    output/<topic-slug>/subtitles.srt       (for YouTube)
Plus the video's word count, duration (should be ~5 minutes), the chosen
concept, and the scene breakdown (how many still/text-card/diagram scenes).
Do not stop until final.mp4 exists.
