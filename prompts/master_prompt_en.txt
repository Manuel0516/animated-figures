You are a code agent with access to a terminal (Bash) in this project —
whether Claude Code, Codex, opencode (with any model: DeepSeek, GLM,
Kimi, etc.) or similar. None of these instructions depend on which
agent or model you are — you only need to read/write files and
run Bash commands.

Your mission: create the FULL production package for a faceless YouTube
video in the animated curiosity channel style (like Whymentary), in the
ENGINEERING FACTS / CURIOSITIES niche, in English. FULLY AUTONOMOUS:
never stop to ask the user anything; from the topic to the final MP4,
you complete every step yourself.

━━━ PART 0: PICK A TOPIC ━━━
Generate 6 video ideas for an engineering-curiosity channel in English.
Type of content: questions about how things are built and why they don't
fall apart, that the viewer never asked but can't ignore once heard.
One topic per video, told narratively, no creator on camera.

Topics that work in this niche:
- Civil engineering: bridges, skyscrapers, dams, tunnels, cranes
- Mechanical engineering: engines, gears, bearings, hydraulics
- Everyday engineering: why windows don't blow out, how traffic lights work
- Materials: steel, concrete, glass, why they behave the way they do
- Famous failures and the lessons they taught (Tacoma Narrows, Challenger)
- Hidden infrastructure: sewers, power grids, water supply

Title patterns that work:
- "Why the [structure] doesn't [fail]"
- "The engineering trick behind [everyday thing]"
- "How [structure] survives [extreme condition]"
- "The [X] that changed engineering forever"
- "What actually happens when [engineered thing] fails"

Evaluate the 6 ideas by viral potential for a curious 25-45 audience.
Auto-pick the best one, mark it with ⭐, and proceed without waiting.
If the user already gave you a topic, use it directly.

━━━ PART 1: SCRIPT ━━━
Write the full script in English (1,100-1,300 words ≈ 7-9 minutes).
Structure:
• HOOK (15s): the most unexpected question or fact about the topic.
  The viewer must think "I didn't know that" within 5 seconds.
• CONTEXT (30s): why this matters more than it seems. Connect it to
  something the viewer already knows (a bridge they cross, a building
  they've seen).
• BODY: 3-4 blocks of ~90s each, each ending with an unexpected mini-twist.
• FINAL FACT: save the most impressive fact for the closing.
• CLOSE + CTA: 2 conclusion sentences + an open question for comments
  + like and subscribe.
Rules:
- Short sentences (8-12 words on average)
- Second-person narrative tone (you)
- No lists or bullets — continuous oral narration
- Concrete, comparable facts ("10 times stronger than", "the equivalent
  of filling a stadium")
- Engineering terms must be explained in plain language the first time
  they appear ("a truss — the lattice of triangles you see under bridges")
- Each body block ends with: "But what nobody expected is..."

━━━ PART 2: SPLIT INTO SCENES ━━━
Split the script into scenes of 4-8 seconds (~12-20 words each). Each
scene is ONE entry in project.json. You decide the best VISUAL for each
scene from these types (this is an ENGINEERING channel: diagrams are
your superpower — prefer them for anything structural, mechanical, or
explanatory):

1. "diagram" — a manim animation built from a declarative spec. USE FOR:
   cross-sections, force/load diagrams, gear trains, flow paths, how
   parts connect. Write the spec JSON yourself (see schemas/diagram.schema.json
   and scripts/render/diagram_scene.py): nodes with labels + optional
   Nerd Font icons, edges with labels, a reveal order. Keep specs simple:
   2-5 nodes, 1-4 edges, reveal in 2-4 steps.
2. "character" — a static stick figure beat ("overview, then zoom into
   detail" transition). Spec: {"pose": "overview"|"point-right", "duration": N}.
   Use sparingly (max 2-3 per video) as narrative punctuation.
3. "still" — an AI-generated image in the channel's MS-Paint doodle
   style. USE FOR: establishing shots, emotional beats, humour, scenes
   that can't be diagrammed. Provide visual.prompt (60-120 words, very
   specific: framing, subject, pose, objects, background — content only,
   NO style instructions; the style is added automatically).
4. "text-card" — bold typographic card. USE FOR: key numbers, the final
   fact, section titles. Just provide visual.text (short, 2-6 words per
   line, max ~4 lines).

Mix at least TWO types per video. A good ratio for engineering:
   ~40% diagrams, ~35% stills, ~15% text-cards, ~10% characters.

━━━ PART 3: WRITE project.json + script.txt ━━━
Create the folder output/<topic-slug>/ and write:
1. script.txt — the full narration text (plain text, no numbering).
2. project.json — array of scenes, each:
   {"index": N, "text": "<narration for this scene>",
    "visual": {"type": "...", ...type-specific fields...}}
   Follow schemas/project.schema.json exactly. index is 1-based, in order.
   Text cards: visual.text is the card text (may differ slightly from
   scene text — it's the ON-SCREEN text, keep it short).
   Diagrams: visual.spec is a RELATIVE path like "diagrams/scene-003.json"
   — write that spec file too, inside output/<topic-slug>/diagrams/.
   Characters: visual.spec like "characters/scene-002.json" — write it too.
   Stills: visual.src like "04.png" (the file run_all.py will generate).

━━━ PART 4: RUN THE PIPELINE ━━━
Run the single command that does EVERYTHING (images, diagram renders,
narration, subtitles, assembly):

    python scripts/run_all.py --dir output/<topic-slug> --lang en

If it fails, read the error, fix the cause (usually a spec field or a
missing visual field), and re-run. run_all.py is idempotent: finished
assets are kept, only what's missing gets (re)built.

━━━ PART 5: REPORT ━━━
When done, list the outputs:
    output/<topic-slug>/final.mp4           (with subtitles)
    output/<topic-slug>/final_clean.mp4     (no subtitles)
    output/<topic-slug>/subtitles.srt       (for YouTube)
Plus the video's word count, duration, and scene breakdown (how many
diagram/still/text-card/character scenes). Do not stop until final.mp4
exists.
